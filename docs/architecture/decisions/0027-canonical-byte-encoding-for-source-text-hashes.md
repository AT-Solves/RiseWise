# ADR-0027: Canonical byte encoding for source text hashes

- **Status:** Accepted (2026-11-03)
- **Decision Register:** DR-071
- **Resolves:** OQ-E16
- **Related:** ADR-0004, ADR-0015 (DR-052), ADR-0021, ADR-0023 (DR-067)

## Context
ADR-0004 gives passages and snapshots SHA-256 content hashes. ADR-0015 / DR-052 defines `contentHash` (whole passage) and `quotedTextHash` (extracted span) over the stored `original`, with spans in Unicode code points. ADR-0021 makes `original` the faithful decoded Unicode text of the acquired bytes, containing only valid Unicode scalar values. No rule defined how such text becomes bytes before hashing (OQ-E16). "UTF-8" alone is ambiguous: some encoders add a byte order mark, and non-standard variants encode some characters differently.

## Decision
A single source text value, hashed independently, is encoded from its exact stored Unicode scalar-value sequence as standard, well-formed UTF-8 and hashed with the algorithm established by ADR-0004.

## Detailed rules
1. **Single text value.** "Single source text value" means one text value hashed independently. Constructions that combine several values or fields are outside this ADR.
2. **Hashed text.** The exact stored Passage `original`, or for `quotedTextHash` its DR-052 code-point span `[start,end)`.
3. **Spans first.** Spans are cut in Unicode code points before encoding; byte offsets are never used.
4. **Encoding.** Standard, well-formed UTF-8 as defined by the Unicode Standard (shortest form). Modified UTF-8 and CESU-8 are not permitted.
5. **No encoder BOM.** No encoder-generated byte order mark is added.
6. **U+FEFF.** A U+FEFF character present in the stored text is content and is encoded like any other character.
7. **No transformation.** No Unicode normalisation, no line-ending conversion and no other transformation before encoding.
8. **Algorithm.** SHA-256 as established by ADR-0004; not redefined here.
9. **Identifiability.** The encoding rule and hash algorithm used for a stored hash must be identifiable so that the hash can be reproduced and verified in the future. This ADR does not decide how that identification is represented, creates no storage fields and defines no algorithm-change mechanism.

## Alternatives considered

| Alternative | Why not chosen |
|---|---|
| UTF-16 or UTF-32 | Byte-order and byte-order-mark variants add ambiguity; no benefit |
| Normalise (NFC/NFD), then encode | Would decide DR-051 implicitly and hash a different sequence from the one DR-052 offsets refer to |
| UTF-8 with an encoder-added byte order mark allowed | One text gets two hashes, and a text without a leading U+FEFF could share bytes with one that has it |
| Unspecified "UTF-8" | Non-standard variants make the bytes non-deterministic |

## Consequences
- Hashes are reproducible across conforming implementations.
- Hashes identify exact stored text: canonically equivalent but differently stored sequences hash differently, by design. Equivalence is a search/normalisation matter (DR-051).
- UTF-8 encoding of scalar values does not depend on the Unicode version, so this rule needs no version pin (unlike segmentation, OQ-E13).

## Non-goals
- Composite constructions (OQ-E17, OQ-E18).
- Acquired-byte hashes (ADR-0021).
- Working-copy normalisation (DR-051 / OQ-E03).
- Unicode segmentation and version (OQ-E13).
- How encoding and algorithm are identified.
- Storage representation or field names.
- The choice, or any change, of hash algorithm (ADR-0004).

## Relationship to existing decisions
- **ADR-0004:** the algorithm is inherited unchanged.
- **ADR-0021:** acquired bytes and their hashes are untouched. *Cross-reference only:* how a decoder treats a byte order mark at the start of acquired bytes is part of the decoding method already recorded under ADR-0021; this ADR creates no decoder requirement.
- **DR-051:** not decided; hashing never operates on working copies.
- **DR-052:** the span coordinate system, unchanged.

## Boundary with E17 and E18
This ADR defines how one text value, hashed independently, becomes bytes. How multiple values or fields are combined, ordered, separated or framed into a snapshot hash (OQ-E17) or a composite EvidenceAnchor hash (OQ-E18) is not decided here; those questions remain open.
